## Snapshot Capabilities and lookup

- `Capabilities` built from the snapshot drives the chart: `kubeVersion`
  `v1.37.0`/minor `37` reach templates and subcharts; `APIVersions.Has
  "route.openshift.io/v1"` flips with the snapshot's discovery list; Bitnami's
  `common.capabilities.psp.supported` renders a PodSecurityPolicy on a 1.20
  snapshot and none on 1.37. (Bitnami common 2.x now hard-codes
  `policy/v1` for PDBs, so that helper no longer depends on KubeVersion.)
- `lookup` from the snapshot inventory: with a `Secret/redis` carrying
  `redis-password` in the snapshot, `common.secrets.passwords.manage` reuses the
  cluster value (rendered base64 equals the snapshot's); with an empty
  inventory the chart generates one, deterministically under the seed. Named
  miss returns an empty map and a list returns `{items: []}`, matching the
  engine's own semantics. The literal design path (`RenderWithClientProvider`
  over client-go's fake dynamic client) answers the same lookups.

## Findings that change the design

1. **`RenderWithClientProvider` and `CustomTemplateFuncs` cannot be combined.**
   In v4.3.0 `Engine.clientProvider` is unexported; `engine.New(*rest.Config)`
   and `RenderWithClientProvider` are the only constructors that set it and
   neither takes custom functions. `initFunMap` copies `CustomTemplateFuncs`
   last, so a custom `lookup` overrides the built-in one. The product installs
   the snapshot-backed `lookup` and the deterministic replacements in one
   `CustomTemplateFuncs` map and needs no `ClientProvider`. Design 3.3 P2
   should say so (or an upstream `Engine` option is proposed; not required).
2. **The replacement list is longer than design 3.3 P2 lists.** Besides
   `randAlphaNum`, `randAlpha`, `randNumeric`, `uuidv4`, `now`, `genCA`,
   `genSelfSignedCert`, `genSignedCert`, `htpasswd`, `bcrypt`, the stock engine
   also varies on `randAscii`, `randBytes`, `randInt`, `shuffle`,
   `genPrivateKey`, `genCAWithKey`, `gen*CertWithKey`, `ago`, and, by time zone,
   `date` and `htmlDate` (sprig formats in the process's local zone). The
   measured "14 keys differ" list is the authoritative set for the parent
   fixture. `derivePassword` is already deterministic (scrypt) and needs no
   replacement.
3. **Helm 4.3 evaluates 2020-12, not merely tolerates it.** `$schema`
   2020-12, `$ref` into `$defs`, `unevaluatedProperties`, `dependentRequired`,
   `dependentSchemas` and `if`/`then` all enforce; `x-fathom-*` keywords are
   ignored by validation as annotations. Error text is jsonschema v6's
   (`at '/persistence/size': '8G' does not match pattern …`), which the
   finding back-mapper can parse into `instanceLocation`.
4. **A remote `$ref` is a network call at render time.** Helm 4.3 registers
   an HTTP(S) loader; offline it fails with a connection error. Contract rule
   for `fathom contract lint`: no `$ref` outside the document (and no `$id`
   that redirects resolution); `.fathom/schema*.json` must stay self-contained.
5. **Bitnami charts ignore any `values.schema.json` in the chart directory.**
   Their `.helmignore` lists `values.schema.json` ("Schema validation
   (temporarily disabled)"), so a schema placed in the chart is silently
   dropped by the loader. `contract lint` must check `.helmignore`, and the
   consultant's overlay schema in `.fathom/contracts/<package>/` is validated
   by fathom itself, never by dropping a file into a vendor chart.
6. **Subchart merge semantics for `contract emit`.** The parent schema is
   validated against the whole coalesced map, so it sees every subchart
   section and `global`; a root `additionalProperties: false` that does not
   list them fails with `additional properties 'child', 'global' not allowed`.
   Each subchart schema is validated against its own section after Helm pushes
   `global` into it, and nothing else (the child fixture's
   `additionalProperties: false` passes). Emitted schemas therefore list
   subchart keys and `global` at the root and allow `global` in every subchart
   schema.
7. **Argo CD 3.5.3 already ships Helm 4.2.1**, and its render is
   document-identical to the SDK render, so the SDK is a faithful stand-in for
   the controller's `helm template` and the schema is enforced there too
   unless `helm.skipSchemaValidation` is set on the Application.

Design impact: sections 3.3 P2 (function list and the ClientProvider wording),
3.8 and 4 (contract rules: self-contained schema, `.helmignore` check, merge
rules for emitted schemas), 3.5 (the seed and the pinned UTC clock are report
inputs). No change to the pipeline order, the finding record or the roadmap.
